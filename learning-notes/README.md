# NamuWiki Trend Monitor — 개발 기록

> 이 문서는 NamuWiki Trend Monitor를 **왜 만들었고**, **어떤 방식으로 구현했으며**, **개발 중 어떤 문제를 해결했는지** 정리한 개인 학습 기록입니다. 프로그램 설치 방법과 사용자용 기능 안내는 저장소 최상위의 [`README.md`](../README.md)를 참고합니다.

## 1. 프로젝트를 시작한 이유

궁금한 것이 생기면 사람들이 자주 찾는 사이트 중 하나가 나무위키다. 많은 사람이 특정 인물, 사건, 작품 등을 검색한다면 그 관심이 실시간 검색어 순위에도 반영될 수 있다고 생각했다.

따라서 **나무위키 실시간 검색어 순위를 주기적으로 확인하면 최근 화제가 되는 주제를 빠르게 발견할 수 있지 않을까?**라는 생각에서 출발했다. 매번 나무위키에 접속해 순위를 확인하기보다, 브라우저가 자동으로 검색어를 수집하고 새로 등장한 이슈만 알려주면 편리할 것 같았다.

이 아이디어를 구현하면서 평소 사용해 보고 싶었던 **Chrome 확장 프로그램(Extension)** 개발도 직접 경험해 보고자 했다.

**목표**

- 나무위키 실시간 검색어 **TOP 10**을 자동으로 가져온다.
- 사용자가 원하는 주기로 검색어를 수집한다.
- 당일 처음 발견한 검색어만 Windows 알림으로 알려준다.
- 팝업에서 최신 TOP 10을 보고, 궁금한 검색어는 나무위키나 아카라이브 검색 페이지에서 확인할 수 있게 한다.

## 2. 사용 기술과 파일별 역할

별도의 서버 없이 **JavaScript, HTML, CSS, Chrome Extension Manifest V3 API**로 구현했다.

| 파일 | 담당 역할 |
| --- | --- |
| `manifest.json` | 확장 프로그램 정보, 권한, 서비스 워커·콘텐츠 스크립트·팝업 등록 |
| `background.js` | 수집 스케줄, 임시 탭 관리, 검색어 비교·저장, Windows 알림 |
| `content.js` | 나무위키 화면의 DOM에서 TOP 10 추출 후 메시지 전송 |
| `popup.html` | 팝업 화면 구조 |
| `popup.js` | 저장된 검색어 출력, `NEW` 표시, 수집 간격 설정, 관련 링크 생성 |
| `popup.css` | 검색어 순위·설정 UI 스타일 |
| `icons/icon128.png` | 확장 프로그램 및 알림에 사용하는 아이콘 |

주요 Chrome API:

- `chrome.alarms`: 주기적 수집 및 임시 탭 정리 예약
- `chrome.tabs`: 수집용 비활성 탭 생성·종료
- `chrome.runtime.sendMessage`: 콘텐츠 스크립트에서 서비스 워커로 결과 전송
- `chrome.storage.local`: 수집 결과·오늘 관측한 검색어·사용자 설정 저장
- `chrome.storage.session`: 현재 수집용 임시 탭 ID 저장
- `chrome.notifications`: 신규 검색어 알림 생성

## 3. 전체 실행 흐름

```text
Chrome 실행 또는 확장 프로그램 초기화
   ├─ 사용자 설정에 맞춰 주기적 수집 알람 등록
   └─ 시작 시 즉시 1회 수집
           ↓
수집용 나무위키 비활성 탭 생성
           ↓
content.js가 페이지에서 TOP 10 추출
           ↓
chrome.runtime.sendMessage()
           ↓
background.js가 검색어 유효성·메시지 발신 탭 확인
           ↓
오늘 관측한 검색어와 비교
   ├─ 새 검색어 없음 → 최신 TOP 10 저장
   └─ 새 검색어 있음 → 최신 데이터 저장 → Windows 알림
           ↓
임시 탭 종료 및 정리 알람 취소
           ↓
다음 수집 시 반복
```

팝업에서는 `chrome.storage.local`의 **가장 최근 성공한 수집 결과**를 읽어 TOP 10과 수집 시각을 보여 준다. 팝업을 열었다는 이유만으로 별도의 수집을 실행하지는 않는다.

## 4. 구현 과정

### 4-1. 나무위키 실시간 검색어 DOM 분석

처음에는 개발자 도구를 열어 검색어 영역의 HTML을 확인했다. 검색어 목록은 `ul` 안의 `li > a` 요소로 표현됐고, 링크의 `href`가 `/Go?q=`로 시작하며 `title` 속성에 검색어가 들어 있었다.

문제는 화면에 보이는 순위가 10개인데, DOM에서 관련 요소가 **11개** 잡힌다는 점이었다. 순환 표시용으로 보이는 중복 항목이 있어, 수집 결과에 중복된 검색어가 들어올 수 있었다.

또한 요소에 붙은 난독화된 클래스 이름은 변경될 가능성이 있어 특정 클래스에 의존하지 않는 방식으로 접근했다.

```javascript
const lists = [...document.querySelectorAll("ul")];

const realtimeList = lists.find(ul => {
    const links = [...ul.querySelectorAll("li a")];
    return links.length >= 10 && links.every(a =>
        a.getAttribute("href")?.startsWith("/Go?q=") &&
        a.hasAttribute("title")
    );
});

const keywords = [...realtimeList.querySelectorAll("li a")]
    .map(a => a.getAttribute("title")?.trim())
    .filter(Boolean);

const top10 = [...new Set(keywords)].slice(0, 10);
```

위 코드는 **목록을 찾았다고 가정한 핵심 부분만 발췌**한 것이다. 실제 코드는 목록 미발견 시 `null`을 반환하고, 최종 개수가 정확히 10개인지도 확인한다.

**배운 점:** 외부 사이트의 DOM을 다룰 때는 특정 CSS 클래스보다 구조·속성을 활용하는 편이 변경에 대응하기 쉽다. 다만 이 방식도 사이트 구조가 바뀌면 수정이 필요하다.

### 4-2. 페이지 로딩 시점 문제

처음 페이지가 열리자마자 검색어가 존재하지 않는 경우가 있었다. 고정된 시점에 한 번만 조회하면 실패할 수 있으므로, `content.js`에서 **1초마다 재시도하고 최대 15번 확인**하도록 구현했다.

- 성공하면 반복 작업을 중지하고 수집 결과를 전송한다.
- 제한 시간 내에 찾지 못하면 실패 로그를 남긴다.
- 확장 프로그램을 새로고침해 예전 콘텐츠 스크립트의 실행 환경이 무효화된 경우를 고려해, 메시지 전송 전에 확장 프로그램 컨텍스트를 확인한다.

실패 시 저장된 이전 검색어를 덮어쓰지 않도록 했다.

### 4-3. 백그라운드에서 검색어 수집하기

단순히 나무위키에 접속했을 때만 데이터를 가져오는 것은 목표와 달랐다. 그래서 `background.js`의 서비스 워커에서 주기적으로 수집 작업을 시작하게 했다.

먼저 서비스 워커에서 나무위키 대문 HTML을 `fetch()`로 가져와 보았지만, 응답 HTML에 기대한 실시간 검색어 요소가 포함되지 않았다. 실제 브라우저 화면에서 동적으로 구성되는 부분이라 판단하고, **비활성 탭을 잠깐 열어 `content.js`가 렌더링된 DOM을 읽게 하는 방법**을 선택했다.

- `chrome.tabs.create({ active: false })`로 수집용 탭 생성
- `content.js`가 TOP 10을 `chrome.runtime.sendMessage()`로 전달
- `background.js`가 메시지의 발신 탭 ID를 관리 중인 탭 ID와 비교
- 처리 후 `chrome.tabs.remove()`로 수집용 탭 종료

**한계:** `active: false`는 사용자가 보고 있던 탭을 전환하지 않을 뿐, 탭 자체를 숨기지는 않는다. 추후 사이트의 데이터 요청 구조를 안정적으로 파악하면 탭 없는 수집을 검토할 수 있다.

### 4-4. 15분 고정 주기에서 사용자 설정으로 확장

처음에는 기능 검증을 위해 1분 주기로 테스트했다. 이후 실제 사용을 위해 **15분을 기본값**으로 정했고, 마지막에는 사용자가 **5분·15분·30분·60분** 중 하나를 선택할 수 있도록 변경했다.

```javascript
const ALLOWED_INTERVALS = [5, 15, 30, 60];

const data = await chrome.storage.local.get("checkIntervalMinutes");
const interval = ALLOWED_INTERVALS.includes(data.checkIntervalMinutes)
    ? data.checkIntervalMinutes
    : 15;
```

팝업에서 `checkIntervalMinutes`를 저장하면, 서비스 워커는 `chrome.storage.onChanged`로 변경을 감지하고 기존 `checkKeywords` 알람을 새 주기로 등록한다. 설정은 `storage.local`에 남으므로 Chrome을 재실행해도 유지된다.

또한 처음에는 알람이 설정된 뒤 **첫 수집까지 15분을 기다려야 하는 문제**가 있었다. 이를 개선하기 위해 `startKeywordCollection()`을 별도 함수로 분리하고, Chrome 시작·확장 프로그램 초기화 시 **즉시 한 번 수집**하도록 했다. 주기 알람은 이후 반복 수집을 담당한다.

### 4-5. 당일 중복 알림 문제 해결

처음에는 **직전 TOP 10**과 현재 TOP 10을 비교했다. 하지만 실제 실검에서는 같은 이슈가 10위 밖으로 나갔다가 다시 진입하는 일이 잦았다. 이 방식은 기존 이슈를 다시 신규 검색어로 판단해 알림을 반복해서 보냈다.

그래서 비교 기준을 **오늘 한 번이라도 관측한 검색어 전체**로 변경했다.

```javascript
const seenSet = new Set(seenKeywords);

const newEntries = currentKeywords
    .map((keyword, index) => ({ keyword, rank: index + 1 }))
    .filter(entry => !seenSet.has(entry.keyword));

const updatedSeenKeywords = [
    ...new Set([...seenKeywords, ...currentKeywords])
];
```

- `currentKeywords`: 마지막으로 수집한 TOP 10
- `seenKeywords`: 오늘 관측한 검색어 전체
- `seenDate`: 누적 기록의 기준 날짜
- `latestNewEntries`: 마지막 수집에서 새로 발견한 검색어와 그 시점 순위

새 날짜가 시작되면 누적 목록을 새로 구성하되, **전날 마지막 TOP 10을 기본 목록으로 이어받아** 자정 직후 기존 검색어가 일괄적으로 신규 알림 처리되지 않도록 했다.

**검증:** 현재 TOP 10을 다시 비교했을 때 신규 검색어가 나오지 않는지 확인했고, 오늘 등장했지만 지금은 순위권 밖에 있는 검색어를 가상의 TOP 10에 재진입시켜 중복 판별이 되지 않는지도 테스트했다.

### 4-6. Windows 알림 및 전송 실패 대비

새 검색어가 발견되면 `chrome.notifications.create()`로 Windows 알림을 생성한다. 알림이 한 번에 너무 많이 뜨지 않도록 **한 번의 수집에서 발견한 신규 검색어를 하나의 알림으로 묶었다.** 표시 공간을 고려해 최대 3개까지 순위와 검색어를 보여주고, 나머지는 `외 N개`로 표시한다.

알림 배너 표시 시간은 Chrome 확장 프로그램이 정확히 지정할 수 없어, **Windows 알림 표시 시간 설정(약 5초)**에 따르도록 했다. 알림 클릭 시 별도 사이트를 여는 기능은 넣지 않았다.

처음에는 신규 검색어를 이미 `seenKeywords`에 저장한 뒤 알림이 실패하면 다음 수집에서 알림 대상에서 빠지는 문제가 있었다. 이를 보완하려고 **`pendingNewEntries`와 `pendingDate`**를 도입했다.

1. 신규 검색어와 이전에 전송 실패한 대기 항목을 합쳐 저장한다.
2. Windows 알림 생성을 시도한다.
3. 생성 성공 시 대기 목록을 비우고, 실패 시 유지한다.
4. 다음 성공적인 수집에서 같은 날짜의 대기 알림을 재시도한다.

이 방식은 **알림 생성 요청 실패에 대비**한 것이지, 사용자가 실제로 알림을 보았음을 보장하지는 않는다. 성공 이후 대기 목록 초기화에 실패하면 중복 전송될 가능성도 남아 있다.

### 4-7. 수집 실패 시 임시 탭 정리

수집이 성공하면 탭이 곧바로 닫혔지만, 검색어를 찾지 못해 메시지가 오지 않으면 탭이 남는 문제가 있었다. 그래서 수집 시작 후 **약 30초 뒤 실행되는 별도의 정리 알람**을 추가했다.

```javascript
await chrome.alarms.create("cleanupMonitorTab", {
    delayInMinutes: 0.5
});
```

- 정상 수집 후에는 탭을 즉시 종료하고 정리 알람을 취소한다.
- 수집에 실패하거나 응답이 없으면 정리 알람을 통해 탭 종료를 시도한다.
- 탭 종료가 실패하면 실제로 탭이 아직 있는지 확인하고, 남아 있다면 추적용 ID를 유지한다.
- 수집용 탭 ID는 `chrome.storage.session`에 기록해 메시지를 보낸 탭을 식별한다.

테스트에서는 별도 `about:blank` 탭을 수집용으로 등록한 뒤 정리 알람만 설정해 **실패 상황을 재현**했고, 자동으로 닫히는지 확인했다.

### 4-8. 팝업 UI와 '이유' 링크

`popup.js`는 `chrome.storage.local`의 `currentKeywords`, `latestNewEntries`, `lastCheckedAt`, `seenDate`를 읽어 화면에 표시한다.

- 검색어 1~10위와 마지막 수집 시각 표시
- 마지막 수집에서 오늘 처음 발견한 검색어에만 `NEW` 배지 표시
- 검색어 텍스트 클릭 시 나무위키 검색 페이지로 이동
- **`이유` 클릭 시 아카라이브 실검 관련 채널에서 해당 검색어의 검색 결과 열기**
- 수집 간격 선택·저장

초기에는 오늘 누적 검색어 수, 최근 신규 검색어 별도 목록도 표시했지만, 화면이 복잡해 보여 제거했다. 개인적으로는 **실검 TOP 10과 필요한 바로가기만 보여주는 간단한 UI**가 목적에 더 잘 맞았다.

아카라이브 기능은 **실검에 오른 이유를 직접 분석하거나 자동 검증하는 기능이 아니다.** 관련 게시글을 직접 확인할 수 있도록 검색 결과로 연결하며, 일치하는 게시글이 없을 수도 있다.

## 5. 테스트 및 확인 내용

| 테스트 | 확인한 결과 |

| 나무위키 검색어 추출 | 중복 제거 후 10개 수집 |
| 자동 수집 후 임시 탭 정리 | 탭 종료 및 정리 알람 제거 확인 |
| 수집 실패 시 정리 | 빈 탭을 이용한 시간 초과 정리 테스트 통과 |

| 사용자 수집 간격 | 설정값 변경 시 알람 주기 변경 확인 |
| 팝업 표시 | TOP 10, `NEW`, 수집 시간 및 링크 확인 |

일부 테스트는 실제 외부 환경을 임의로 변경한 것이 아니라 **저장된 데이터를 활용한 모의 테스트**였다. 사이트 구조 변경, 네트워크 불안정, 알림 권한 변경 등 모든 장기 운영 상황이 검증된 것은 아니다.

## 6. 아쉬운 점과 향후 개선 아이디어

- **탭 없는 수집:** 비활성 탭이 순간적으로 나타나는 사용성 문제를 줄이기 위해 공개된 데이터 요청 경로가 있는지 추가 확인
- **HTML 변경 대응:** 나무위키의 검색어 영역 구조가 바뀌면 선택자 수정 필요
- **실검 이유 기능 고도화:** 현재는 아카라이브 검색 결과로 연결하는 수준이며, 추후 관련 글 존재 여부나 게시 시각을 확인해 더 정확한 링크 제공 가능
- **장기 안정성:** 일자 변경 시점, 저장소 동시 갱신, 알림 실패 이후 재시도 등 예외 상황 보강

## 7. 이번 프로젝트에서 배운 점

이번 프로젝트에서는 화면에서 데이터를 추출하는 코드뿐 아니라, **브라우저 확장 프로그램의 실행 환경을 이해하고 여러 구성 요소를 연결하는 작업**이 중요했다.

특히 다음을 직접 경험했다.

- Manifest V3의 서비스 워커와 콘텐츠 스크립트는 서로 다른 실행 환경에서 동작한다.
- DOM이 동적으로 생성되는 페이지에서는 **로딩 시점과 재시도 방식**이 수집 성공률을 좌우한다.
- 최신 상태만 저장하면 '신규'의 의미가 불분명해진다. 요구사항에 맞는 **상태 저장 기준**이 필요하다.
- 정상 실행뿐 아니라 **실패했을 때 자원을 정리하는 로직**도 기능의 일부다.
- 기능을 많이 보여주는 것보다 사용 목적에 맞는 **단순한 팝업 UI**가 더 유용할 수 있다.
