# NamuWiki Trend Monitor — 개발 기록

> 이 문서는 **기술 설명**, **만든 이유**, **배포 경험**을 정리한 개인 개발 기록이다. 프로그램의 기능과 설치 방법은 저장소 최상위의 [README.md](../README.md)를 참고한다.
>
> **배포 상태:** Chrome 웹스토어 **검토(심사) 제출 단계**까지 진행했다. 심사 승인 및 실제 게시 완료를 의미하지 않는다.

## 1. 기술 설명

### 1-1. 기술 스택과 구조

별도의 백엔드 서버 없이 **JavaScript, HTML, CSS, Chrome Extension Manifest V3**를 사용했다. 브라우저의 서비스 워커가 수집을 예약하고, 콘텐츠 스크립트가 웹페이지의 검색어를 추출하며, 팝업은 로컬 저장소에 보관된 결과를 표시하는 구조다.

| 구성 요소 | 역할 |
| --- | --- |
| `manifest.json` | 확장 프로그램 정보, 권한, 서비스 워커·콘텐츠 스크립트·팝업 등록 |
| `background.js` | 실행 주기 관리, 수집용 탭 생성·정리, 신규 검색어 판별, 알림 전송 |
| `content.js` | 나무위키 대문의 DOM에서 실시간 검색어 TOP 10 추출 |
| `popup.html` | 검색어 목록과 사용자 설정 화면 구성 |
| `popup.js` | TOP 10 렌더링, `NEW` 표시, 검색·이유 링크, 설정 읽기·저장 |
| `popup.css` | 검색어 목록, 버튼, 알림 ON/OFF 토글 스타일 |
| `icons/icon128.png` | 확장 프로그램과 Windows 알림에 사용할 아이콘 |

사용한 Chrome API도 역할별로 나눌 수 있다.

- **`chrome.alarms`**: 주기적 수집 및 수집 실패 시 정리 작업 예약
- **`chrome.tabs`**: 비활성 수집용 탭 생성과 종료
- **`chrome.runtime.sendMessage`**: 콘텐츠 스크립트에서 서비스 워커로 검색어 전달
- **`chrome.storage.local`**: 최신 TOP 10, 당일 등장한 검색어, 사용자 설정, 알림 대기 목록 저장
- **`chrome.storage.session`**: 현재 수집 중인 임시 탭 ID 관리
- **`chrome.notifications`**: 신규 검색어를 Windows 알림으로 전달

### 1-2. 전체 동작 흐름

```text

         ├─ 사용자 설정에 맞는 반복 수집 알람 예약
         └─ 시작 시 검색어 즉시 1회 수집
                         │
                         ▼
              나무위키 대문 비활성 탭 생성
                         │
                         ▼
              content.js에서 DOM 분석
                         │
                         ▼
                검색어 TOP 10 추출
                         │
                         ▼
                runtime.sendMessage()
                         │
                         ▼
              background.js에서 검증
                         │
                         ▼
         당일 관측 목록(seenKeywords)과 비교
                ├─ 기존 검색어 → 알림 없음
```

팝업은 **마지막으로 성공한 수집 결과**를 보여준다. 팝업을 열 때마다 나무위키를 다시 수집하는 구조는 아니다.

### 1-3. 실시간 검색어 TOP 10 추출

개발자 도구로 나무위키 대문의 검색어 영역을 조사했다. 검색어는 `ul` 내부의 `li > a`에 나타났고, 관련 링크의 `href`는 `/Go?q=`로 시작하며 `title` 속성에 검색어가 담겨 있었다.

초기에는 난독화된 CSS 클래스에 의존한 선택자를 시도했지만, 해당 클래스를 안정적으로 찾지 못했다. 그래서 **클래스 이름 대신 HTML 구조와 속성**을 기준으로 검색어 목록을 탐색했다.

```javascript
const lists = [...document.querySelectorAll("ul")];

const realtimeList = lists.find(ul => {
    const links = [...ul.querySelectorAll("li a")];
    return links.length >= 10 && links.every(a =>
        a.getAttribute("href")?.startsWith("/Go?q=") &&
        a.hasAttribute("title")
    );
});

// realtimeList를 찾은 이후의 핵심 추출 로직
const keywords = [...realtimeList.querySelectorAll("li a")]
    .map(a => a.getAttribute("title")?.trim())
    .filter(Boolean);

const top10 = [...new Set(keywords)].slice(0, 10);
```

화면에는 10개가 표시됐지만 DOM에서는 중복을 포함해 11개 항목이 확인되는 경우가 있었다. **`Set`으로 중복을 제거하고 상위 10개만 추출**해 해결했다. 실제 코드에서는 목록을 찾지 못하면 `null`을 반환하고, 최종 결과가 정확히 10개인지도 검증한다.

또한 검색어 영역이 늦게 생성될 수 있어 `content.js`에서 **1초 간격으로 최대 15회 재시도**하도록 했다. 수집에 실패하면 이전에 저장한 정상 데이터를 덮어쓰지 않는다.

### 1-4. 서비스 워커와 콘텐츠 스크립트의 통신

처음에는 `background.js`에서 `fetch()`로 나무위키 대문 HTML을 요청해 봤지만, 받은 HTML에서 필요한 실시간 검색어 목록을 확인하지 못했다. 페이지에서 동적으로 구성되는 영역을 읽어야 했기 때문에 다음 방식을 채택했다.

1. `background.js`가 `chrome.tabs.create({ active: false })`로 대문을 연다.
2. `content.js`가 렌더링된 페이지의 TOP 10을 추출한다.
3. `chrome.runtime.sendMessage()`로 검색어를 서비스 워커에 전송한다.
4. 서비스 워커는 발신 탭 ID가 현재 관리 중인 임시 탭과 일치하는지 확인한다.
5. 수집 처리가 끝나면 임시 탭을 닫는다.

확장 프로그램을 새로고침한 뒤 남아 있던 콘텐츠 스크립트에서 메시지 전송 오류가 발생하기도 했다. 이에 확장 프로그램 실행 컨텍스트를 확인하고 전송 오류를 처리하도록 보완했다.

**제약:** `active: false`는 화면의 활성 탭을 바꾸지 않을 뿐, 브라우저 탭 표시줄에 새 탭이 잠깐 보일 수 있다. 현재는 정상 작동과 구현 복잡도를 고려해 이 방식을 유지했다.

### 1-5. 자동 수집 주기와 임시 탭 정리

초기 기능 검증은 1분 간격으로 수행했다. 이후 기본 주기를 15분으로 정하고 **5·15·30·60분 중 사용자가 선택**할 수 있도록 변경했다.

```javascript
const ALLOWED_INTERVALS = [5, 15, 30, 60];

const data = await chrome.storage.local.get("checkIntervalMinutes");
const interval = ALLOWED_INTERVALS.includes(data.checkIntervalMinutes)
    ? data.checkIntervalMinutes
    : 15;
```

사용자가 팝업에서 수집 간격을 저장하면 `chrome.storage.onChanged`가 변경을 감지하고 반복 알람을 새 주기로 등록한다. 설정값은 브라우저를 다시 실행해도 유지된다.

또 하나 발견한 문제는 처음 실행 시 **첫 수집까지 설정한 간격만큼 기다려야 한다는 것**이었다. 수집 시작 로직을 `startKeywordCollection()`으로 분리한 뒤, Chrome 시작 및 확장 프로그램 초기화 시 한 번 즉시 호출하고 이후 반복 알람으로 수집하도록 바꿨다.

수집 실패 시 임시 탭이 계속 남는 문제도 있었다. 이를 해결하기 위해 **약 30초 후 정리하는 별도 알람**을 두었다.

```javascript
await chrome.alarms.create("cleanupMonitorTab", {
    delayInMinutes: 0.5
});
```

정상 수집 시에는 바로 탭을 종료하고 정리 알람도 제거한다. 응답이 없으면 정리 알람이 탭 종료를 시도한다. 종료 실패 시에는 실제 탭 존재 여부를 확인하고, 아직 열려 있다면 추적용 ID를 유지하도록 했다. 수집 중복 실행도 관리 중인 탭 ID를 확인해 방지했다.

### 1-6. 당일 신규 검색어 판단 및 중복 알림 방지

처음에는 **직전 TOP 10과 현재 TOP 10**을 비교했다. 하지만 검색어가 10위 밖으로 나갔다가 다시 들어오면 이미 봤던 이슈인데도 신규 알림이 반복되는 문제가 발생했다.

그래서 비교 기준을 **그날 한 번이라도 관측한 전체 검색어**로 변경했다.

```javascript
const seenSet = new Set(seenKeywords);

const newEntries = currentKeywords
    .map((keyword, index) => ({ keyword, rank: index + 1 }))
    .filter(entry => !seenSet.has(entry.keyword));

const updatedSeenKeywords = [
    ...new Set([...seenKeywords, ...currentKeywords])
];
```

저장 데이터의 역할은 다음과 같다.

| 저장 항목 | 의미 |
| --- | --- |
| `currentKeywords` | 최근 수집된 TOP 10 |
| `seenKeywords` | 당일 한 번 이상 등장한 모든 검색어 |
| `seenDate` | 누적 검색어 기록의 기준 날짜 |
| `previousKeywords` | 날짜 변경 시 비교 기준이 되는 이전 수집 목록 |
| `latestNewEntries` | 가장 최근 수집에서 처음 발견한 검색어와 순위 |
| `lastCheckedAt` | 마지막 정상 수집 시각 |

날짜가 변경되면 전날 마지막 TOP 10을 새 기준 목록으로 이어받아, 자정 직후 같은 검색어에 알림이 한꺼번에 발생하지 않도록 했다.

현재 목록을 다시 비교하는 테스트와, **당일 등장했다가 순위권에서 이탈한 검색어를 가상으로 재진입시키는 테스트**를 통해 중복 판별을 확인했다.

### 1-7. Windows 알림과 사용자 ON/OFF 설정

새로운 검색어가 발견되면 `chrome.notifications.create()`로 Windows 알림을 생성한다. 한 번의 수집에서 신규 검색어가 여러 개라면 알림 하나로 묶고, 최대 3개를 순위와 함께 표시하며 나머지는 `외 N개`로 나타낸다.

알림 표시 시간은 확장 프로그램이 정확히 5초로 제어하는 것이 아니라 **Windows 알림 표시 시간 설정**을 따른다. 알림 클릭 시 별도 페이지를 자동으로 열지는 않는다.

알림 생성 요청이 실패했을 때 해당 검색어를 놓치는 문제를 완화하기 위해 `pendingDate`, `pendingNewEntries`를 저장한다. 실패한 알림은 같은 날짜의 다음 정상 수집에서 재시도하고, 알림 생성에 성공하면 대기 목록을 비운다. 이는 사용자에게 배너가 실제로 보였음을 보장하는 장치는 아니다.

마지막으로 사용자가 **Windows 알림을 ON/OFF로 전환하는 토글 스위치**를 추가했다.

- 기본값은 **ON**이며, 설정은 `chrome.storage.local`에 저장된다.
- **OFF** 상태에서도 검색어 수집과 TOP 10 갱신은 계속된다.
- OFF 동안 새롭게 발견한 검색어는 알림 대기 목록에 쌓지 않는다.
- 다시 ON으로 변경해도 OFF 동안의 검색어를 한꺼번에 알리지 않는다.
- 실제 알림 생성 함수를 콘솔에서 호출해 **OFF일 때 알림 없음 / ON일 때 알림 발생**을 검증했다.

### 1-8. 팝업 UI와 아카라이브 연결

팝업은 **현재 TOP 10과 마지막 수집 정보에 집중**하도록 단순하게 구성했다. 초기에는 당일 누적 검색어 개수와 신규 검색어 별도 목록도 표시했지만, 사용 목적에 비해 화면을 복잡하게 만들어 삭제했다.

현재 주요 UI는 다음과 같다.

- 최근 수집된 TOP 10 표시
- 가장 최근 수집에서 당일 처음 등장한 검색어에 `NEW` 배지 표시
- 검색어 클릭 시 나무위키 검색 페이지 열기
- **`이유` 버튼** 클릭 시 아카라이브 실검 관련 채널의 해당 검색어 검색 결과 열기
- 수집 간격 선택·저장, Windows 알림 ON/OFF 토글
- 마지막 수집 시각과 기록 기준일 표시

아카라이브 기능은 **실검 원인을 프로그램이 자동으로 분석하거나 확정하는 기능이 아니다.** 사용자가 관련 게시글을 직접 확인하도록 검색 결과로 연결하며, 일치하는 게시글이 없을 수도 있다.

### 1-9. 검증한 항목과 한계

| 점검 내용 | 확인 결과 |
| --- | --- |
| 실시간 검색어 수집 | 중복 제거 후 TOP 10 확인 |
| Chrome 실행 시 수집 | 재시작 후 수집 시각 갱신 확인 |
| 주기 변경 | 5분·15분 설정 변경 시 알람 주기 반영 확인 |
| 신규 검색어 자동 알림 | 실제 신규 검색어 발견 후 Windows 알림 확인 |
| 당일 중복 방지 | 동일 검색어 재수집 및 가상 재진입 테스트 통과 |
| 정상 수집 후 탭 정리 | 임시 탭 ID·정리 알람 제거 확인 |
| 수집 실패 후 탭 정리 | `about:blank`를 이용한 시간 초과 테스트 통과 |
| Windows 알림 ON/OFF | OFF일 때 차단, ON일 때 생성, 설정 유지 확인 |
| 팝업 | TOP 10, `NEW`, 이유 링크 및 설정 UI 확인 |

실제 사이트의 HTML 변경, 장기간 네트워크 장애, 드문 비동기 경합 등 **모든 운영 환경을 검증한 것은 아니다**. 비활성 탭을 만드는 방식과 외부 사이트 구조에 대한 의존성은 이후 개선 과제다.

## 2. 만든 이유

사람들은 궁금한 인물이나 사건, 콘텐츠가 생겼을 때 나무위키를 자주 찾아본다. **많은 사람이 무엇을 궁금해하는지 보여주는 실시간 검색어 순위를 활용하면, 최근 화제가 된 이슈에 빠르게 접근할 수 있지 않을까?**라는 생각이 프로젝트의 출발점이었다.

하지만 매번 사이트에 접속해 순위를 확인하는 방식은 번거로웠다. 그래서 **검색어 목록을 자동으로 확인하고, 이전에 보지 못했던 이슈만 알려주는 도구**를 만들고 싶었다. 동시에 Chrome 확장 프로그램을 직접 구현해 보면서 브라우저 API, 서비스 워커, 콘텐츠 스크립트, 로컬 저장소를 사용하는 방법을 익히고자 했다.

개발하면서 목표도 구체화됐다. 단순히 검색어 순위가 바뀔 때마다 알림을 보내는 것이 아니라, **사용자에게 실질적으로 새로운 화제가 생겼을 때만 알려줘야 한다**고 판단했다. 검색어가 순위 밖으로 나갔다가 재진입하는 상황을 겪으며 당일 누적 목록을 기준으로 알림을 판단하도록 설계를 바꾼 이유다.

이후 사용성을 고려해 수집 주기 설정, 알림 ON/OFF, 관련 게시글 검색 링크를 추가했다. 최종적으로는 **최근 화제를 빠르게 발견하되, 불필요한 알림과 조작은 최소화하는 확장 프로그램**을 목표로 했다.

## 3. 배포 경험

### 3-1. GitHub 저장소 정리

개발한 소스 코드를 GitHub에 업로드하고, 사용자용 설명과 개인 개발 기록을 분리했다.

```text
NamuWikiTrendMonitor/
├── README.md                    # 기능, 설치 및 사용 안내
├── PRIVACY.md                   # 개인정보처리방침
├── learning-notes/
│   └── README.md                # 기술 설명, 만든 이유, 배포 경험
└── namuwiki-trend-monitor/
    ├── manifest.json
    ├── background.js
    ├── content.js
    ├── popup.html
    ├── popup.js
    ├── popup.css
    └── icons/
        └── icon128.png
```

- 저장소: [NamuWikiTrendMonitor](https://github.com/Seoyoungeun/NamuWikiTrendMonitor)
- `README.md`는 **처음 설치하는 사용자**를 위한 문서로 구성했다.
- `learning-notes/README.md`는 **구현 과정과 문제 해결을 기록**하는 문서로 분리했다.
- 파일명에 공백이 들어가 `README .md`가 별도로 올라간 문제를 Git 명령어로 정리하면서 파일명과 스테이징 상태를 확인하는 경험도 했다.

### 3-2. Chrome 웹스토어 패키지 준비

로컬 개발에서는 `chrome://extensions`에서 압축 해제된 폴더를 불러왔지만, 웹스토어 등록에는 **확장 프로그램 실행 파일을 ZIP으로 제출**해야 했다.

- `manifest.json`이 ZIP 내부 최상위에 오도록 압축 구조를 확인했다.
- GitHub 문서나 개인 개발 기록은 확장 프로그램 실행 패키지에서 제외했다.
- 변경 기능을 반영하면서 패키지 버전과 업로드 파일을 구분해 관리했다.

### 3-3. 스토어 등록정보와 이미지 준비

Chrome 웹스토어 개발자 대시보드에서 패키지 업로드 외에도 별도의 등록정보를 작성해야 했다.

- 확장 프로그램 이름과 한국어 설명
- 검색어 TOP 10, Windows 알림, 사용자별 수집 간격 및 `이유` 링크에 대한 기능 안내
- 카테고리와 언어 설정
- 128×128 아이콘 및 실제 팝업을 보여주는 스크린샷
- 나무위키·아카라이브의 **공식 서비스가 아닌 개인 개발 프로젝트**임을 알리는 문구

개발을 마치는 것과 사용자가 스토어에서 이해하고 설치할 수 있게 소개하는 작업은 별개의 과정이라는 점을 체감했다.

### 3-4. 권한 근거 및 개인정보 보호 항목 작성

Chrome 웹스토어는 확장 프로그램이 요청하는 권한의 사용 목적을 구체적으로 설명하도록 요구했다. 프로젝트에 사용한 권한과 근거를 실제 코드에 맞춰 정리했다.

| 권한 | 제출 시 설명한 사용 목적 |
| --- | --- |
| `storage` | 실시간 검색어, 당일 중복 감지 기록, 사용자 수집 간격 및 알림 설정 보관 |
| `alarms` | 반복 수집 예약 및 수집 실패 시 임시 탭 정리 |
| `notifications` | 신규 실시간 검색어의 Windows 알림 제공 |
| `https://namu.wiki/*` | 나무위키 대문의 실시간 검색어 목록 추출 |

특히 **호스트 권한은 추가 심사 대상이 될 수 있다는 경고**를 확인했고, 단순히 필요하다고만 작성하는 대신 *어느 사이트에서 무엇을 수집하고 언제 탭을 닫는지*를 설명했다.

또한 JavaScript는 확장 프로그램 패키지 내부 파일로 실행하고, 외부 사이트에서는 검색어 **데이터만 읽는 방식**이어서 원격 코드 실행 여부와 외부 데이터 접근을 구분하여 신고했다.

개인정보 관련 항목에서는 실제로 처리하는 데이터의 종류를 확인하고, GitHub에 공개한 [`PRIVACY.md`](../PRIVACY.md) 문서를 웹스토어 개인정보처리방침 URL로 연결했다. 개인정보처리방침에는 로컬 저장 데이터, 사용 목적, 외부 사이트 연결 및 문의 경로를 안내했다.

게시 과정에서는 **개발자 프로그램 정책 준수 확인, 게시자 연락처 이메일 등록·인증 등의 요구사항**도 확인했다.

### 3-5. 심사 제출과 현재 상태

스토어 등록정보와 개인정보·권한 설명을 준비하고, 최신 기능을 포함한 확장 프로그램에 대해 **Chrome 웹스토어 검토(심사) 제출 단계까지 진행**했다.

> **현재 확인된 배포 경험은 '심사 제출'까지다.** 심사 승인, 일반 사용자 대상 게시, 실제 설치 수 등은 아직 이 기록에서 완료 사실로 다루지 않는다. 승인 및 게시가 확인되면 결과와 웹스토어 링크를 추가할 예정이다.

### 3-6. 배포 과정을 통해 배운 점

이번 경험을 통해 **로컬에서 정상 작동하는 프로그램을 만드는 것과 실제 배포 가능한 확장 프로그램을 준비하는 것은 다르다**는 점을 배웠다.

- 기능 구현뿐 아니라 **사용 권한을 최소화하고 각 권한의 필요성을 설명**해야 한다.
- 스토어 설명과 스크린샷은 실제 구현 기능과 일치해야 한다.
- 로컬 저장 기능만 사용하더라도 **데이터 처리 방식과 개인정보처리방침을 명확히 공개**해야 한다.
- 기능 변경 후에는 GitHub 코드와 배포 ZIP의 버전이 달라지지 않도록 관리해야 한다.
- 배포 상태는 **심사 제출 / 승인 / 게시 완료**를 구분해 정확하게 기록해야 한다.
